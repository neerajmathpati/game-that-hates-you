Implementation order and technical acceptance criteriaAppendix A - Pseudocode and interfaces1. Technical direction and architectureUse a single Next.js application with client-side game runtime. The server should render the landing shell and static pages, while the actual game runs inside a browser component. The adaptive engine, session telemetry and level state stay client-side. This removes the need for a database, API server or runtime AI provider in the MVP.Architecture decision:  Next.js 16.3.x + TypeScript + Phaser 3 for the game runtime, React for shell/UI, and local/session browser storage only for non-sensitive settings. The default deployment is one Vercel project.Why this architectureFast deployment.  Vercel provides zero-configuration support for Next.js and Git-based deployments can automatically create preview/production deployments.Low operational risk.  No backend service is required for the core game loop.Offline resilience.  Once the page and assets are loaded, the game can continue without external API calls.Easy judging/demo.  A single URL demonstrates the complete adaptive loop.Extensible later.  A server/API can be added later for analytics, accounts or a remote AI personality without rewriting the core game engine.2. Behavior capture and adaptive engineEvent recording rulesUse a compact ring buffer; target max 2,000-5,000 events per session.Emit semantic events at decision points rather than every animation frame.Keep continuous movement aggregates separately so raw frame data is unnecessary.Normalize timing to session-relative milliseconds; never capture wall-clock timestamps unless an analytics feature explicitly requires them.Drop redundant events when they exceed a configurable rate limit.Feature extractionFeatureFormula / methodDefault thresholdConfidence ruleleftRatioleft / (left + right)0.68Need &gt;= 2 decision points; confidence grows with repeated evidence.jumpRatejumps / activeSecondsConfigurableNeed &gt;= 3 jumps and cross-check hazard proximity.medianHesitationmedian decision-to-choice ms900 ms for cautious, 350 ms for rushNeed &gt;= 3 decisions.repeatScoresame route pattern / comparable retries0.70Need &gt;= 3 comparable sequences.exploreScoreoptional interactions / opportunities0.55Need &gt;= 2 opportunities.rushScorenormalized speed + low hesitation0.65Two independent signals required.Confidence and hysteresisEach trait has a score and confidence. Score represents strength of evidence; confidence represents quantity and consistency of evidence. A trait becomes active only when confidence &gt;= 0.65 and score &gt;= 0.65. Once active, it should remain active until its score falls below 0.45 across multiple observations. This prevents the game from oscillating when the player changes strategy once.Adaptation selectionAt the beginning of each level, sort active traits by a weighted impact score. Select at most two primary counters for Levels 2-4. Level 5 may select up to three. Apply a counter budget so total hazard pressure remains bounded.TraitCounter exampleCounterplayLEFT_BIASEDLeft route looks faster but contains a telegraphed hazard.Take right route or wait for the safe timing.RIGHT_BIASEDRight shortcut collapses after commitment.Use left route or alternate timing.JUMP_HEAVYA familiar obstacle is safer when passed on the ground.Walk under / around it.RUSHERFast entry triggers a timed gate.Slow down and observe.CAUTIOUSA waiting zone changes after prolonged idle.Commit within a reasonable timing window.REPETITIVESame input sequence stops working.Change route/order.EXPLORERA suspicious side object becomes a harmless decoy while the obvious route matters.Stop over-interacting and proceed.7. Level and hazard architectureHand-authored templates + adaptive modifiersDo not generate geometry from scratch at runtime. Each level is a hand-authored template with tagged decision points and modifier hooks. The AdaptationEngine supplies parameters such as hazard activation, route safety, timing windows and decoy placement.interface LevelTemplate {  id: string;  sceneKey: string;  durationTargetSec: number;  decisionPoints: DecisionPoint[];  modifierSlots: ModifierSlot[];}interface ModifierSlot {  id: string;  supports: TraitId[];  intensity: 0 | 1 | 2 | 3;}interface AdaptationPlan {  level: number;  activeTraits: TraitId[];  modifiers: Record&lt;string, { intensity: number; parameter: number }&gt;;}Level safety invariantsEvery decision point has at least one non-counter route.An adaptive hazard cannot spawn directly on the player or remove an already-established safe recovery area.Counter modifiers must be deterministic for the same profile and seed, unless an experiment explicitly adds controlled randomness.If no confident traits exist, use a neutral modifier set.If the player repeatedly changes strategy, lower counter intensity rather than escalating forever.8. Frontend and rendering implementationNext.js integrationUse App Router for route structure and metadata.Keep the game page a client component boundary only where Phaser is mounted.Load Phaser only on the play route to avoid increasing the landing page bundle unnecessarily.Use a loading screen that initializes the game canvas and assets before accepting input.Keep game loop updates inside Phaser; React should receive only coarse-grained events such as observation, death, pause and completion.Rendering modelUse Phaser Canvas/WebGL renderer selected by the library/runtime. Target a fixed logical resolution with responsive scaling. Keep world coordinates independent of device pixel ratio. Prefer bitmap or vector-like assets with small memory footprints.Input modelKeyboard: Arrow keys / A-D movement, Space or W for jump, R for retry.Touch: large left/right/jump controls only when touch is detected.Gamepad support is optional and out of MVP.9. Persistence, privacy and securityThe MVP does not require an account or backend. Behavior observations are ephemeral session data. Persist only user-facing preferences such as mute or reduced motion if desired.AreaRequirementPrivacyDo not collect name, email, precise location, device identifier or sensitive attributes.TelemetryNo remote telemetry in MVP unless explicitly added and documented.StorageSession profile stays in memory; optional settings use localStorage.SecurityNo secrets in client bundle. No API keys are required for the core game.Third-party assetsUse original or properly licensed assets; keep a license file for external dependencies.ResetProvide a full reset action that clears behavior state and restarts from baseline.10. Performance and accessibilityPerformance targetsKeep the landing route lightweight; defer Phaser/game assets until the play experience is requested.Avoid per-frame React state updates.Keep event logging semantic and bounded.Prefer small sprite/audio assets and avoid shipping unused content.Use browser devtools and Vercel deployment checks to identify oversized bundles or asset failures before submission.AccessibilityKeyboard controls must be fully usable.Critical feedback cannot rely on color alone.Provide mute and reduced-motion options.Text overlays should meet readable contrast and avoid rapid unreadable flashes.Add accessible labels to non-canvas UI controls.12.
